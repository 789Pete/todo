## Scope Notes

**PRD AC4 (user analytics dashboard with session patterns and engagement metrics):** Descoped. Tracking click history and session funnels requires new models and background data collection — beyond a single story. This story delivers a simple staff-only stats page showing aggregate task/user/tag counts via a `@staff_member_required` view.

**PRD AC5 (database backup automation with point-in-time recovery):** Descoped. PythonAnywhere's backup mechanism is a scheduled console task; there is no application code to write. A `scripts/backup_db.py` script is documented in `docs/architecture/deployment-architecture.md` — no new code needed.

**PRD AC1 (rollback capabilities):** Automated rollback (re-triggering a previous deploy on failure) is out of scope. The deployment verification step already causes the CI run to fail, enabling manual rollback via `git revert` + push. This story focuses on gating the deploy job on the CI test job.

This story covers PRD ACs 1–3 and 6–7 within the above boundaries, and delivers a scoped version of AC4.

## Acceptance Criteria

1. The deploy workflow (`.github/workflows/deploy.yml`) only runs when the CI workflow on `main` succeeds — implemented via `workflow_run: workflows: ["CI"] / types: [completed]` trigger with a gate on `github.event.workflow_run.conclusion == 'success'`; the deploy workflow passes `GIT_COMMIT_SHA=${{ github.event.workflow_run.head_sha }}` to the PythonAnywhere console command so the correct commit is deployed
2. Sentry init in `production.py` is enhanced with `environment='production'` and `release=os.environ.get('GIT_COMMIT_SHA', 'unknown')` so each deploy is associated with a specific commit in the Sentry releases UI; the existing `SENTRY_DSN`-conditional guard is preserved
3. Production logging in `production.py` is improved from console-only WARNING to INFO-level structured logging: a `RotatingFileHandler` writing to `logs/django.log` (10 MB, 5 backups) with a `verbose` formatter (`{levelname} {asctime} {module} {message}`); the `apps` logger is configured at INFO so task/account events are captured; the `logs/` directory is created at deploy time (added to `scripts/` or documented in deploy notes)
4. Two additional health check endpoints are added to `todo_project/urls.py`: `GET /health/ready/` returns `{"status": "ready"}` (200) when the DB is reachable or `{"status": "not_ready"}` (503) on DB error; `GET /health/live/` returns `{"status": "alive"}` (200) unconditionally — both following the existing `health_check` function pattern in the same file
5. Failed login attempts are logged at WARNING level via Django's `user_login_failed` signal: a new `apps/accounts/signals.py` connects to `django.contrib.auth.signals.user_login_failed` and logs `"Failed login attempt for username: {username} from IP: {ip}"` using `logger = logging.getLogger('apps.accounts')`; the signal is registered in `apps/accounts/apps.py` `ready()` method
6. A staff-only monitoring dashboard is accessible at `GET /tasks/monitoring/` (`staff_member_required` decorator, redirects non-staff to login); the view queries aggregate stats — `total_users`, `active_users_today` (last_login within 24 h), `total_tasks`, `tasks_created_today`, `total_tags` — and renders `tasks/monitoring.html` showing these counts in a simple Bootstrap card grid; non-staff users (including authenticated regular users) receive a redirect to `/accounts/login/`

### Deploy Workflow — `workflow_run` Trigger Notes

The `workflow_run` event fires even when the CI workflow fails; the `if:` condition gates execution:

```yaml
on:
  workflow_run:
    workflows: ["CI"]
    branches: [main]
    types: [completed]

jobs:
  deploy:
    if: github.event.workflow_run.conclusion == 'success'
```

The triggering commit SHA is `github.event.workflow_run.head_sha` (not `github.sha`). Pass it as an env var to the PythonAnywhere console command:

```bash
git -C ~/todo fetch origin && git -C ~/todo checkout $GIT_COMMIT_SHA
```

### Logging Configuration Pattern

Minimal additive change to existing config in `production.py`:

```python
import os
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "verbose": {
            "format": "{levelname} {asctime} {module} {message}",
            "style": "{",
        },
    },
    "handlers": {
        "console": {"class": "logging.StreamHandler"},
        "file": {
            "class": "logging.handlers.RotatingFileHandler",
            "filename": os.path.join(BASE_DIR, "logs/django.log"),
            "maxBytes": 1024 * 1024 * 10,
            "backupCount": 5,
            "formatter": "verbose",
        },
    },
    "root": {"handlers": ["console"], "level": "WARNING"},
    "loggers": {
        "django": {"handlers": ["console"], "level": "ERROR", "propagate": False},
        "apps": {"handlers": ["console", "file"], "level": "INFO", "propagate": False},
    },
}
```

`BASE_DIR` is imported via `from .base import *` — it is available. The `logs/` dir must exist on the server before the first request; add `mkdir -p ~/todo/logs` to the deploy command.

### Failed Login Signal

```python
# apps/accounts/signals.py
import logging
from django.contrib.auth.signals import user_login_failed
from django.dispatch import receiver

logger = logging.getLogger("apps.accounts")

@receiver(user_login_failed)
def log_failed_login(sender, credentials, request, **kwargs):
    username = credentials.get("username", "<unknown>")
    ip = request.META.get("HTTP_X_FORWARDED_FOR", request.META.get("REMOTE_ADDR", "unknown"))
    logger.warning("Failed login attempt for username: %s from IP: %s", username, ip)
```

### Staff Monitoring Dashboard

Simple function-based view using `@staff_member_required` — no class-based view needed. Stats queries:

```python
from datetime import timedelta
from django.contrib.admin.views.decorators import staff_member_required
from django.contrib.auth import get_user_model
from django.shortcuts import render
from django.utils import timezone

@staff_member_required
def monitoring_dashboard(request):
    User = get_user_model()
    from apps.tasks.models import Tag, Task
    context = {
        "total_users": User.objects.count(),
        "active_users_today": User.objects.filter(
            last_login__gte=timezone.now() - timedelta(days=1)
        ).count(),
        "total_tasks": Task.objects.count(),
        "tasks_created_today": Task.objects.filter(
            created_at__gte=timezone.now() - timedelta(days=1)
        ).count(),
        "total_tags": Tag.objects.count(),
    }
    return render(request, "tasks/monitoring.html", context)
```

## Risk and Compatibility

- **`workflow_run` trigger timing:** Deploys fire asynchronously after CI completes, not immediately on push. This is acceptable and is the standard GitHub Actions pattern. The head SHA is passed explicitly so the right commit is deployed.
- **`logs/` directory missing on first deploy:** The file handler will raise at startup if `logs/` doesn't exist. Mitigated by adding `mkdir -p ~/todo/logs` to the deploy command (Task 1.3).
- **`staff_member_required` on PythonAnywhere:** Redirects non-staff authenticated users to `/accounts/login/?next=...`. This is standard Django Admin decorator behaviour — no special handling needed.
- **Signal import in `apps.py` `ready()`:** If signals import models that aren't ready, an `AppRegistryNotReady` error can occur. The signal module only imports from `django.contrib.auth.signals` (no model import at module level), so this is safe.
- **Rollback:** All changes are additive (no new model, no migration). `deploy.yml` trigger change is isolated to CI/CD. Reverting any file restores prior behaviour.
