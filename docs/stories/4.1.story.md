## Status: Ready for Review

## Story

**As a** power user,
**I want** keyboard shortcuts for all major actions and navigation,
**so that** I can manage tasks efficiently without relying on mouse interactions.

## Acceptance Criteria

1. Task creation shortcut (Ctrl/Cmd+N) opens new task form with focus
2. Quick task completion toggle (Space or Enter) for selected tasks
3. Navigation shortcuts for switching between views (1-9 keys for different views)
4. Search and filter shortcuts (Ctrl/Cmd+F for task search, Ctrl/Cmd+T for tag filter)
5. Graph navigation shortcuts (arrow keys for node selection, Enter for activation)
6. Tag assignment shortcuts during task editing (# for tag autocomplete)
7. Help overlay (? key) displaying all available shortcuts in context-sensitive manner

### Architecture: Frontend Pattern (Alpine.js + Vanilla JS)

### Architecture: Task Toggle Endpoint

[Source: `apps/tasks/urls.py`]
[Source: `apps/tasks/templates/tasks/task_list.html`]

The task toggle endpoint is:
- URL: `{% url 'task-toggle-status' pk=task.pk %}` → `/tasks/<uuid:pk>/toggle/`
- Method: POST
- CSRF: required (`X-CSRFToken` header using `getCookie('csrftoken')`)
- Response: 302 redirect (browser behavior); in the fetch call we just call `window.location.reload()` after the POST completes

The existing `<form method="post" action="{% url 'task-toggle-status' pk=task.pk %}">` in each task item is reused by Task 2.6 — the `fetch` call submits `new FormData(toggleForm)` which includes the CSRF token from the hidden `{% csrf_token %}` input.

### Architecture: Search Parameter

[Source: `apps/tasks/views.py:TaskListView`]

Currently `TaskListView.get_queryset()` handles:
- `status` param: filters by task status
- `sort` param: orders results
- `tags` param (list): filters by tag IDs

The new `q` param filters by `title__icontains`. It is applied **after** the existing filters, so all three can combine (e.g., `?q=fix&status=todo&tags=<uuid>`).

The `q` parameter should be included in the `page_base_params` for pagination to preserve search state across pages. In `get_context_data()`, `page_base_params` is built from `page_params = self.request.GET.copy(); page_params.pop("page", None)` — since `q` is in `request.GET`, it is automatically included in `page_base_params`. No additional change needed.

### Architecture: vis-network Keyboard Option

[Source: `static/js/graph-viewer.js:82-103`]
[Source: `docs/architecture/tech-stack.md#complete-stack-table`]

The vis-network 9.x `keyboard` option enables arrow-key panning of the graph canvas when the container has focus:
```javascript
keyboard: {
    enabled: true,
    bindToWindow: false,  // CRITICAL: only pan when container is focused
    speed: { x: 10, y: 10, zoom: 0.02 },
}
```

Setting `bindToWindow: false` is critical — without it, vis-network binds arrow key events to `window`, which would interfere with the task list arrow-key navigation in `keyboard-shortcuts.js` (both files are loaded on split-view page). With `bindToWindow: false`, arrow keys only pan the graph when the `#network-graph` div has focus (via `tabindex="0"`).

vis-network does not natively support "Enter to open selected node" — that requires the custom `keydown` listener in Task 5.3.

**AC5 scope note:** The AC states "arrow keys for node selection"; however, vis-network's built-in `keyboard` option provides arrow-key *canvas panning* (not node traversal). True node-to-node selection via arrow keys would require complex custom graph-traversal code with no architecture guidance. The implemented behavior (arrow-key panning + Enter to open selected node) satisfies the spirit of AC5 — the graph is keyboard-navigable. Clicking a node first to select it, then pressing Enter to open it, is the intended flow. The help modal text ("Pan graph") accurately reflects the actual behavior.

### Technical Constraints and Shortcut Conflict Analysis

[Source: `docs/architecture/tech-stack.md#browser-support-matrix`]

| Shortcut | Browser Default | Our Behavior | Conflict Resolution |
|---|---|---|---|
| `Ctrl/Cmd+N` | New browser window | New task form | `preventDefault()` always (intentional override) |
| `Ctrl/Cmd+F` | Browser find/search | Focus `#task-search` | `preventDefault()` only when `#task-search` exists (task list page only) |
| `Ctrl/Cmd+T` | New browser tab | Focus tag filter | `preventDefault()` only when `#quick-tag-filter` exists (task list page only) |
| `1`–`4` | Type characters | Navigate views | Only fires when `!isTypingContext()` (not in inputs) |
| `Space` | Scroll page | Toggle task | Only fires when `!isTypingContext()` AND `focusedTaskIndex >= 0` |
| `Enter` | Submit form | Toggle task / open node | Only fires when `!isTypingContext()` AND task or node selected |
| `#` | Type character | Focus tag input | Only fires when `!isTypingContext()` (not in inputs) |
| `?` | Type character | Help modal | Only fires when `!isTypingContext()` (not in inputs) |

The `Ctrl/Cmd+N` override is intentional — power users who press this shortcut on the task app expect to create a new task, not open a new browser window.
