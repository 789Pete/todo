## Story

**As a** user,
**I want** the network graph to load quickly and respond smoothly to interactions,
**so that** visual navigation enhances rather than hinders my productivity.

## Acceptance Criteria

1. Initial graph load completes in under 2 seconds for typical user data (50-200 tasks)
2. Smooth 60fps animations during zoom, pan, and node interactions
3. Graph rendering optimized for various screen sizes and device capabilities
4. Progressive loading shows graph skeleton while data loads to prevent blank states
5. Interaction responsiveness under 500ms for click, hover, and selection actions
6. Memory usage optimized to prevent browser slowdown with large datasets
7. Graceful degradation on older browsers or devices with limited JavaScript support

### N+1 Query Problem in graph_builder.py

**Current code** (N+1 — one query per tag):
```python
# apps/visualization/graph_builder.py lines 102–106
if seen_tag_ids:
    tags = Tag.objects.filter(id__in=seen_tag_ids).prefetch_related("tasks")
    for tag in tags:
        task_count = tag.tasks.filter(user=user).count()  # 1 query per tag!
```

**Fixed code** (single annotated query):
```python
from django.db.models import Count, Q

if seen_tag_ids:
    tags = Tag.objects.filter(id__in=seen_tag_ids).annotate(
        user_task_count=Count("tasks", filter=Q(tasks__user=user), distinct=True)
    )
    for tag in tags:
        task_count = tag.user_task_count  # pre-computed in single query
```

**Query count before fix** (for a user with T tasks and K unique tags used):
- 1 task query (with prefetch_related)
- K tag-count queries (one per tag)
- 2 total-count queries
= K+3 queries total

**Query count after fix**:
- 1 task query (with prefetch_related)  ← keep prefetch_related for task.tags.all() in the loop
- 1 annotated tag query
- 2 total-count queries
= 4 queries total (regardless of K)

### vis-network Physics Tuning

vis-network 9.x defaults to the `barnesHut` solver. The current code does not specify a solver or tune any physics parameters, so vis-network uses its built-in defaults. Explicitly configuring `barnesHut` with tuned parameters and disabling physics after stabilization significantly improves performance for graphs with 50-200 nodes.

**Key parameters**:
- `gravitationalConstant: -3000` — nodes repel each other (negative), keeps graph spread out
- `springLength: 120` — edge preferred length in pixels
- `damping: 0.3` — how quickly nodes slow down (0 = no damping, 1 = instant stop)
- `stabilization.updateInterval: 25` — how often to re-render during stabilization (ms)
- `adaptiveTimestep: true` — allows vis-network to skip frames when physics is fast

**Disabling physics after stabilization** prevents ongoing CPU usage once the graph settles:
```javascript
network.once('stabilized', function () {
    network.setOptions({ physics: false });
});
```
When users drag nodes, vis-network re-enables physics temporarily for that node, then re-stabilizes — this is the expected vis-network behavior and requires no additional code.

### Browser Feature Detection

`URLSearchParams` and `fetch` are used at the top of `graph-viewer.js` before `initializeGraph()` is called. If either is absent (IE11, very old browsers), the current code would throw a `TypeError` on `new URLSearchParams()`. Adding a detection guard at the top of the `DOMContentLoaded` callback prevents this.

Supported browser matrix (from architecture):
- Chrome 90+ (2021+) — `URLSearchParams` since Chrome 49, `fetch` since Chrome 42
- Firefox 88+ — fully supported
- Safari 14+ — fully supported
- Edge 90+ — fully supported

The detection guard (`typeof fetch === 'undefined'`) ensures no JS errors appear in the browser console for unsupported browsers, and users see a friendly message instead.

import pytest
from unittest.mock import patch
from apps.visualization.graph_builder import build_graph_data
from apps.accounts.tests.factories import UserFactory
from apps.tasks.tests.factories import TagFactory, TaskFactory


@pytest.mark.django_db
class TestGraphBuilderQueryCount:
    def test_build_graph_data_avoids_n_plus_one_queries(self, django_assert_num_queries):
        user = UserFactory()
        tags = TagFactory.create_batch(3, user=user)
        for i, tag in enumerate(tags):
            task = TaskFactory(user=user)
            task.tags.add(tag)

        with django_assert_num_queries(5):
            build_graph_data(user)

    def test_build_graph_data_returns_truncated_false_for_small_dataset(self):
        user = UserFactory()
        TaskFactory.create_batch(2, user=user)
        result = build_graph_data(user)
        assert result['stats']['truncated'] is False

    def test_build_graph_data_truncates_at_max_tasks(self):
        user = UserFactory()
        TaskFactory.create_batch(3, user=user)
        with patch('apps.visualization.graph_builder.MAX_TASKS_PER_GRAPH', 2):
            result = build_graph_data(user)
        assert result['stats']['truncated'] is True
        task_nodes = [n for n in result['nodes'] if n['id'].startswith('task-')]
        assert len(task_nodes) == 2

### Constraints and Scope Notes

- AC2 (60fps) and AC5 (<500ms interactions) depend heavily on the user's hardware and the number of visible nodes. The physics tuning (Task 4) is the primary lever available without replacing vis-network. These ACs are satisfied at the architecture level by the design choices (vis-network 9.x, barnesHut solver) — not by writing deterministic server-side tests.
- AC4 ("progressive loading skeleton"): The existing spinner from Story 3.1 (`container.innerHTML = '<div class="spinner-border ...">...'`) already prevents blank states. The truncation warning (Task 3) adds meaningful feedback for the most impactful case. A full skeleton with placeholder node shapes would require significant additional JS with no architecture guidance, so is out of scope.
- The `once('stabilized')` callback disables physics globally. If a user rapidly drags multiple nodes, physics may not re-engage between drags on very old hardware — this is an acceptable UX trade-off per the architecture's stated browser support floor.
