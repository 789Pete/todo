## Status: Approved

## Story

**As a** user,
**I want** powerful search capabilities that help me find tasks quickly,
**so that** I can locate relevant work without scrolling through long lists.

## Scope Notes

**PRD AC3 (relevance ranking based on user interaction patterns):** Descoped. Tracking user interactions (click history, open frequency) requires a new model and background data collection — beyond a single story. This story implements a simple relevance sort: when `q` is active and no explicit sort is chosen, title matches are shown before description-only matches (annotated with a `title_match` flag).

**PRD AC4 (saved searches with persistence):** Descoped. Creating a `SavedSearch` model requires a migration and CRUD views — a separate story. This story instead adds a "Share Search" button that copies the current filtered URL to the clipboard, enabling bookmark-based search saving at zero backend cost.

**PRD AC5 (suggestions based on user history):** Scoped to task-title autocomplete only. Tag autocomplete already exists (`/tasks/tags/autocomplete/`). This story adds `/tasks/search-suggest/` returning matching task titles for the search input dropdown — no history or ranking beyond `icontains` match.

This story covers all 7 PRD ACs with the scope boundaries above.

## Acceptance Criteria

1. The `q` search param matches against **both** `title` and `description` fields (`Q(title__icontains=q) | Q(description__icontains=q)`); the existing `title__icontains`-only filter is replaced
2. A `priority` filter param (`?priority=high|medium|low`) is supported by `TaskListView`; the UI shows "All / High / Medium / Low" priority filter buttons beneath the status row, following the same pattern as status buttons; the active priority is highlighted with `active` class
3. `due_after` and `due_before` date params are supported by `TaskListView` (ISO date strings, silently ignored if malformed); the UI provides two `<input type="date">` fields labelled "Due after" and "Due before" that navigate on change via JS (updating the URL param while preserving other filters)
4. When `q` is present and no explicit `sort` param is set, the queryset is annotated with `title_match` (`Case(When(title__icontains=q, then=1), default=0, output_field=IntegerField())`) and ordered `-title_match, -created_at` so title matches appear before description-only matches
5. Matching search terms in task titles are wrapped in `<mark>` tags in `task_list.html` via a new `highlight` template filter in `task_tags.py`; the `<mark>` element is styled in `base.css` with a yellow background (`background: #fff3cd; padding: 0 2px; border-radius: 2px`)
6. A new `GET /tasks/search-suggest/?q=...` endpoint (`TaskSearchSuggestView`) returns up to 8 matching task titles as JSON `[{"title": "..."}]`; results are scoped to the authenticated user; requires login (`LoginRequiredMixin`); typing in `#task-search` triggers this endpoint and shows a dropdown list of suggestions; clicking a suggestion fills the input and submits (navigates with `?q=<title>`)
7. Active priority and date-range filters are shown as dismissible pills in the existing filter display strip (matching the style of active tag pills); dismissing removes that param from the URL while preserving others; the task count in the page heading (`My Tasks (N)`) reflects the filtered result count and is **always** shown when any filter (`q`, `status`, `priority`, `tags`, `due_after`, `due_before`) is active
8. A "Share Search" button (link icon, `btn-outline-secondary btn-sm`) appears next to the heading when any filter is active; clicking it copies `window.location.href` to the clipboard and shows a transient tooltip "Copied!" for 2 seconds via JS

### Priority Filter URL Pattern

Follow the status filter pattern exactly. Priority buttons link to `?priority=high` while preserving other params. Use `_build_tag_add_url` / `_build_tag_remove_url` as reference for how to build URLs that preserve params — or build similar URL helpers for priority/dates, or construct inline in the template using `request.GET.urlencode` tricks.

The simplest approach for priority dismiss URL: build it in `get_context_data()` the same way `clear_tags_url` is built — pop `priority` from a copy of `request.GET` and return the encoded string.

### Date Range Filter UI

Use Bootstrap's native `<input type="date">` — no third-party datepicker. An `onchange` JS handler is sufficient; no form submit button needed. Example:

```javascript
document.querySelectorAll('.date-range-input').forEach(function(input) {
    input.addEventListener('change', function() {
        var params = new URLSearchParams(window.location.search);
        if (this.value) { params.set(this.dataset.param, this.value); }
        else { params.delete(this.dataset.param); }
        params.delete('page');
        window.location.search = params.toString();
    });
});
```

Use `data-param="due_after"` and `data-param="due_before"` on the inputs.

### Highlight Template Filter — Security Note

The `highlight` filter must use `django.utils.safestring.mark_safe` only after escaping the input value. Use `django.utils.html.escape(value)` before substitution to prevent XSS:

```python
from django import template
from django.utils.html import escape, mark_safe
import re

@register.filter
def highlight(value, query):
    if not query:
        return value
    escaped_value = escape(value)
    escaped_query = re.escape(escape(query))
    highlighted = re.sub(
        escaped_query,
        lambda m: f'<mark>{m.group()}</mark>',
        escaped_value,
        flags=re.IGNORECASE,
    )
    return mark_safe(highlighted)
```

In the template use `{{ task.title|highlight:current_search }}` — **do not** add `|safe` separately; the filter already returns `SafeString`.

### Performance

All filter fields used in Task 2 and 3 already have DB indexes:
- `priority`: `models.Index(fields=['user', 'priority'])` (models.py line 132)
- `due_date`: `models.Index(fields=['user', 'due_date'])` (models.py line 134)

The `title__icontains` and `description__icontains` use `LIKE` which cannot use a btree index, but for MVP user datasets this is acceptable. PostgreSQL trigram index (`pg_trgm`) can be added post-MVP if needed. The `<200ms` AC7 target is achievable for datasets under 10K tasks with the existing indexes on surrounding filter fields.

## Risk and Compatibility

- **XSS in `highlight` filter:** Mitigated by escaping `value` with `django.utils.html.escape()` before inserting `<mark>` tags (see Dev Notes).
- **Suggest dropdown accessibility:** Add `role="listbox"` on `<ul>` and `role="option"` on each `<li>`; ensure Escape key closes the dropdown. Keyboard navigation within dropdown (↑/↓) is a nice-to-have, not required.
- **`get_queryset()` called twice in `get_context_data()`:** `self.get_queryset().count()` for `result_count` duplicates the query. This is acceptable at MVP scale (both queries are fast); cache with `self._cached_qs` if needed.
- **`description__icontains` LIKE scan:** No trigram index. For MVp datasets (<5K tasks per user) this is acceptable. If slow, add SQLite FTS or PostgreSQL trigram index post-MVP.
- **Rollback:** All changes are additive (no new model, no migration). Revert `views.py`, `urls.py`, `task_tags.py`, `task_list.html`, `base.css`, `keyboard-shortcuts.js` to restore prior state.
