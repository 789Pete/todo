## Acceptance Criteria

1. A database migration adds a compound index `(user, position)` on the `Task` model to support the default task ordering query `['position', '-created_at']` without a full table scan per user
2. Django's database cache backend is configured: `DummyCache` in development/test environments, `DatabaseCache` in production (cache table created via `python manage.py createcachetable` on deployment)
3. The graph API endpoint (`/api/graph/`) caches its response per user + filter parameters for 60 seconds using Django's low-level cache API; the cache is invalidated by `post_save` and `post_delete` signals on `Task` and `Tag`
4. The graph viewer persists node layout positions to `localStorage` after the graph stabilises, and restores them on the next page load — eliminating the re-layout delay on repeat visits; a "Reset Layout" button clears the saved positions and re-runs stabilisation
5. When the graph API response includes `stats.truncated: true` (>500 tasks), a visible warning banner is displayed in both the graph-only view and the split view informing the user that only the first 500 tasks are shown
6. When the authenticated user has more than 300 tasks, a dismissible soft-info notice is displayed at the top of the task list page suggesting the user use filters or tags to narrow their view

### Cache Architecture

[Source: `docs/architecture/security-performance.md#caching-strategy`]

**Development/Test**: `DummyCache` — no-op, never actually caches. Keeps tests simple and avoids shared state.

**Production**: `DatabaseCache` backed by `cache_table`. Requires one-time setup:
```bash
python manage.py createcachetable
```

**Graph API cache key pattern**:
```
graph_data_v{version}_user_{user_id}_tag_{filter_tag}_status_{filter_status}
```

Version is stored as a separate cache key (`graph_cache_version_{user_id}`) that is incremented on every Task/Tag save or delete. This avoids Django's lack of pattern-based cache deletion in DatabaseCache.

**Cache TTL**: 60 seconds (graph queries are the most expensive in the application, typically requiring 3–4 DB queries with aggregation).

## Risk and Compatibility

- **Cache version key bootstrap**: On a fresh deployment (no cache table data), `cache.incr()` on a non-existent key will fail — `incr()` on a non-existent key raises `ValueError`. Wrap in try/except and initialise to 0 if not found, or use `cache.get_or_set()` before incr.
- **localStorage quota**: Browsers cap localStorage at ~5MB. A graph with 500 nodes × 2 floats is ~16KB — well within limits. Wrap all localStorage calls in try/catch (already in plan).
- **Rollback**: Cache settings are environment config only — reversible by removing the CACHES block. Signal file can be deleted and `apps.py` reverted. Migration can be reversed (`python manage.py migrate tasks 00XX-1`).
- **SQLite (local dev)**: Index migration is safe on SQLite. DummyCache is no-op — no cache table needed locally.
